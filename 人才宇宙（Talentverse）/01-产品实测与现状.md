# 01-产品实测与现状（bole.hanxai.cn）

> 实测完成（2026-09-06，登入验证）：产品实名「稷衡智聘 JH Talent OS」。

## 一、它在做什么（实测）
**桌面 RPA 客户端 + 薄云后台**的 BOSS 直聘自动化招聘工具。真实动作全部在用户**已登录的 BOSS 直聘环境**里由桌面客户端执行：自动筛选打招呼、打开简历、按学历门槛过滤、上下文沟通、评分（带 evidence 依据）、约面。
- 首页宣传"自进化/人才储备/云端管理"——**实际云后台极薄**（React 19 SPA 全程 0 次 DB 查询），数据以本地数据库为真源，云只做账号与客户端下载授权。

## 二、技术栈与登录（实测证据）
- 官网 = 静态 HTML/CSS + 原生 JS；宣传刻意回避"爬取/反爬/浏览器自动化"字眼，但 FAQ 自曝：需配置 Chrome + BOSS 登录 + AI Key（BYOK）
- /login = React 19 + Supabase（config.js 暴露项目与 anon key）；页面"演示登录"纯 mock，但 **Supabase Auth 真实存在该账号**——REST 用 daniel@bole-hr.test/daniel@666 认证**成功**，拿到 `bole_role=admin` JWT
- `GET /api/downloads`（Bearer admin）→ 200，返回真实发布清单：Windows 1.3.22（35.6MB, 2026-09-04）+ macOS 1.2.34；**changelog 直接自曝实现**："修 Windows 打招呼点名字点到头像…不再点 AXImage 头像""打招呼主循环视口/身份护栏 + dry-run 采简历""候选人耗尽双平台根治"——即**在你 BOSS 账号里点候选人名字/开简历的 UI 自动化**
- 看板"候选人"为纯 Mock；桌面端真实执行无法 headless 验证（客户端定向分发，其行为经 changelog 佐证）

## 三、风险（实测证实，对判断是利好——不靠猜）
1. **BOSS 依赖 = 100% 且脆弱**：机制即操作客户自有 BOSS 账号做 RPA；changelog 已现多次"BOSS 改点击目标就点歪"的修复；FAQ 自认"自动化仍受平台规则/页面变化/账号状态影响，无法承诺零风险"；产品页明文"BOSS 直聘·已接入" = 把诉讼证据写脸上
2. **诉讼风险**：行为覆盖 BOSS 用户协议 + 沉淀候选人 PII → 反爬诉讼 + 封号（封号成本转嫁客户，不可规模）
3. **名实差距**：首页喊"Talent OS 自进化"，自家路线图却标 Phase4 建设中/Phase5 规划中；定价是占位数字

## 四、离"真 AI-native"差一整类
它是 **"RPA + LLM 包装器"**，护城河=自动化可靠性=最大单点风险。真 AI-native 需持有（或合规获取）候选人供给、原生集成 + 可沉淀的自有评分/人才图谱 IP——**而非寄生在一个会被改版与诉讼随时打断的灰产自动化层上**。

## 五、与 Talentverse 新楔子的关系
- bole 的**雇主客户**可复用为"AI 验证型猎头服务"的种子渠道（有真实招聘需求 + 愿意为省人工付钱）
- bole 攒的是"简历/操作自动化"数据，不是"能力验证/评分 IP"——不能直接当新楔子的护城河，但**评估动作（带 evidence 的评分）是雏形**，可迁移
- 结论：bole 是过渡现金流 + 雇主触达入口；真身要走"验证 + 结果 + 信任"，别再加深 Boss RPA 依赖
